### TOP-1: 「固定費」フラグは家計簿レベルか個人レベルか？

- **回答**: **(B) 個人レベル** ✅
- **重要度**: High
- **状況**:
  - 要件定義書 §4.1「カテゴリ設定（ユーザー個別）」: 「ユーザーは、自身が使用する支出カテゴリを『固定費』として設定できる」 → **個人レベル**
  - CLAUDE.md「主要ドメイン」: 「支出カテゴリは『固定費』フラグを持てる」「家計簿レベルで管理（管理者のみ編集可）」 → **家計簿レベル**
  - 両者で記述が食い違っている
- **問い**: 固定費フラグはどちらのレイヤーで管理しますか？
  - **(A)** 家計簿レベル（管理者が「家計簿の支出カテゴリ X は固定費」と一括設定。全メンバー共通。月初コピーは X の全明細を対象）
  - **(B)** 個人レベル（メンバーごとに「私はカテゴリ X を固定費扱いにする」と設定可。月初コピーは『各メンバーが固定費とした支出カテゴリの自分自身の明細のみ』が対象）
- **影響**:
  - ドメインモデル: カテゴリエンティティの属性 or `PersonalCategoryPreference` 値オブジェクトへ
  - DB スキーマ: `categories.is_fixed_cost` か `user_category_preferences.is_fixed_cost` か
  - 固定費自動コピーバッチ: 対象明細の検索クエリが変わる（全メンバー or 各メンバー個別）
  - 月次予算と固定費の関係: 予算は家計簿レベルなので、(B) なら「予算カテゴリは固定費」と「ユーザーAは固定費認定だがユーザーBは認定しない」が混在し得る
- **関連指摘**: U-02

### TOP-2: 「家計簿を作成する」操作のアクターはどう表現するか？

- **回答**: **(B) 現状維持** ✅（家計簿を管理する UC を分割せず、作成も管理者の操作として扱う。「未所属ユーザーが操作した時点で管理者ロールが付与される」を暗黙のルールとし、図上はノートで補足）
- **重要度**: High
- **状況**:
  - 要件定義書 §3 用語定義: 「管理者 = 家計簿の作成者」「1 家計簿に 1 人のみ（作成者本人）」
  - ユースケース図: 「家計簿を管理する（作成・編集・削除）」を `管理者ユーザー` ロールに紐付け
  - **論理矛盾**: 家計簿がまだ存在しない時点では、そのユーザーは管理者ロールを持たない（管理者は「家計簿の作成者」と定義されるため）
- **問い**: 以下のいずれの方針でユースケース図を整理しますか？
  - **(A)** 「家計簿を作成する」のアクターを「ログイン済みユーザー（ロール未確定）」に変更し、事後条件として「作成者が管理者となる」をノートで明示。「家計簿を編集する／削除する」は管理者ユーザー
  - **(B)** 「家計簿を管理する」を分割せず現状維持（管理者ロールに集約）し、作成も管理者の操作として扱う（暗黙に「未所属ユーザーが操作した時点で管理者ロールが付与される」とみなす）
  - **(C)** その他（具体的に）
- **影響**:
  - 図の構造（アクターの数・汎化関係・UC 分割）
  - 設計時の認可ロジック（家計簿作成エンドポイントの認可は何ベースで判定するか）
- **関連指摘**: U-01

### TOP-3: 退会・脱退・メンバー除外の v1 スコープ確定

- **回答**: **v1 では考えない** ✅
  - 家計簿からの脱退（メンバー側）: **v1 スコープ外**
  - 管理者によるメンバー除外: **v1 スコープ外**
  - 管理者退会のシステム制御: **v1 では実装しない**（要件定義書 §11 の「運用カバー（管理者は家計簿削除を必ず先に実施）」を継続）
- **重要度**: High
- **状況**:
  - 要件定義書 §1.3 In Scope: 「アカウント退会（収支データは家計簿に残す）」
  - 要件定義書 §1.3 Out of Scope: 「管理者権限の委譲機能（管理者退会時は運用でカバー）」
  - 要件定義書 §11 リスク: 「管理者は家計簿削除を必ず先に実施」を運用カバー
  - ユースケース図: 「アカウントを退会する」のみ存在。**家計簿からの脱退・メンバー除外は不在**
  - 業務フロー図: 「家計簿削除（任意）」「アカウント退会（任意）」のみで、脱退・除外は不在
- **問い**:
  - **(Q3-a)** メンバーは自分の意思で家計簿から脱退できますか？
    - (A1) 可能（脱退後は別の家計簿に参加可能、収支明細は『退会済みユーザー』表示で残る）
    - (A2) 不可（家計簿から抜けたいなら「アカウント退会」を行う運用。1 ユーザー 1 家計簿ルール下で家計簿の移動は不可）
  - **(Q3-b)** 管理者がメンバーを家計簿から除外する操作は v1 で必要ですか？
    - (B1) 必要
    - (B2) 不要（運用カバー）
  - **(Q3-c)** 管理者の退会操作はシステム上どう制御しますか？
    - (C1) 家計簿が存在する管理者の退会はシステムが拒否（先に家計簿削除を強制）
    - (C2) 警告のみで退会可能（退会後の家計簿は実質「孤児」状態だが、メンバーは引き続き利用可能。新規招待・カテゴリ編集・予算編集は誰もできない）
    - (C3) その他（具体的に）
- **影響**:
  - 退会フローの実装（バリデーション or 警告のみ）
  - 「退会済みユーザー」概念の発生条件（脱退も含むか否か）
  - メンバー一覧 UI の機能（除外ボタンの要否）
  - スコープ外なら要件定義書 §1.3 Out of Scope に「家計簿脱退・メンバー除外」を明記
- **関連指摘**: U-03 / U-04

### A. 認証・プロフィール／退会

#### QA-A1: LINE 公式アカウントの友だち追加導線は？

- **回答**: **(B) アプリ外でカバー** ✅（招待時に LINE で URL を送る運用で吸収。アプリ内導線は提供しない）
- **重要度**: Medium
- **背景**: 要件定義書 §7「LINE Messaging API（公式アカウント）経由 Push 通知 - ユーザー側で公式アカウントの友だち追加が必要」と記載されているが、ユーザーが友だち追加するための導線（アプリ内 or アプリ外）が未確定。Push 通知関連のユースケースもこれに依存する。
- **問い**: LINE 公式アカウントの友だち追加はどこから行いますか？
  - (A) アプリ内（初回ログイン時にチュートリアル画面で QR コード／追加リンクを提示）
  - (B) アプリ外（招待時に LINE で URL を送る運用で吸収。アプリ内導線なし）
  - (C) その他
- **影響**: 「公式アカウントを友だち追加する」をユースケースとして図に追加するか否か。チュートリアル UI の要否。
- **関連指摘**: U-16

#### QA-A2: 通知の ON/OFF 個人設定は v1 で必要？

- **回答**: **(A) 必要、単純な ON/OFF のみ** ✅ → 「通知設定を管理する」UC を追加。`User.push_notification_enabled` フィールド（boolean）を持たせる
- **重要度**: Medium
- **背景**: チャット送信時に他メンバー全員に Push 通知を出すと、業務時間中などで不要な通知が発生し得る。ユースケース図に通知設定 UC は無い。
- **問い**: Push 通知をユーザー個別に ON/OFF する設定は v1 で必要ですか？
  - (A) 必要（時間帯フィルタ含む or 単純な ON/OFF のみ）
  - (B) 不要（一律で送る、または LINE 公式アカウント側のミュート機能で代替）
- **影響**: 「通知設定を変更する」ユースケースの追加要否。`User.notification_preference` フィールドの要否。
- **関連指摘**: U-08

### C. 家計簿への参加（招待 URL）

#### QA-C1: 未使用かつ有効な招待 URL の手動無効化は v1 で必要？

- **回答**: **(B) 不要** ✅（24 時間で自動失効するため運用カバー）
- **重要度**: Medium-High
- **背景**: 要件定義書 §4.1「期限切れ・使用済みの URL は管理者が再発行できる」とあるが、まだ有効な URL を手動で無効化する手段が明記されていない。共有相手間違い等のリカバリ手段が無い。
- **問い**: 管理者が「まだ有効期限内・未使用」の招待 URL を手動で無効化する機能は必要ですか？
  - (A) 必要（共有相手を間違えた・キャンセルしたい等の運用を想定）
  - (B) 不要（24 時間待てば自動失効するので運用カバー可）
- **影響**: 「招待 URL を無効化する」ユースケースの追加要否。
- **関連指摘**: U-05

#### QA-C2: 招待 URL は同時に何本まで有効？

- **回答**: **(B) 1 本のみ** ✅（新規発行で既存の有効 URL は自動無効化）
- **重要度**: Medium
- **背景**: 「1 回限り」とあるが、複数本同時発行できるかは未確定。例: 2 人を別々のタイミングで招待したい場合。
- **問い**: 同時に有効な招待 URL は何本まで発行できますか？
  - (A) 複数本可（メンバー数の上限まで or 無制限）
  - (B) 1 本のみ（新規発行で既存の有効 URL は自動無効化）
- **影響**: 招待 URL テーブルの主キー戦略、発行 API の挙動、UI の表示（有効中の URL 一覧 or 最新のみ）。
- **関連指摘**: U-05

#### QA-C3: 招待 URL 参加時のフロー詳細は？

- **回答**:
  - (Q3-a) 招待 URL 参加は「LINEログイン → プロフィール登録 → 家計簿参加」の 3 ステップ → 既定の解釈通り
  - (Q3-b) **(B1) エラー表示（参加不可）** ✅ → 「既に家計簿に所属しているため参加できません」を表示。TOP-3「脱退・移籍は v1 スコープ外」と整合
- **重要度**: Medium
- **背景**: 業務フロー図では「招待 URL アクセス → LINE ログイン・プロフィール登録 → 家計簿に参加」という直列フロー。ユースケース図には include 関係が無い。また、既にログイン済みかつ別家計簿に所属するユーザーが招待 URL を開いた場合の挙動も未確定（1 ユーザー 1 家計簿ルール）。
- **問い**:
  - (Q3-a) 招待 URL からの参加は「LINEログイン → プロフィール登録 → 家計簿参加」の 3 ステップで合っていますか？
  - (Q3-b) 既にログイン済みかつ別家計簿所属のユーザーが招待 URL を開いた場合の挙動は？
    - (B1) エラー表示（「既に家計簿に所属しています」）
    - (B2) 移籍確認ダイアログ（前家計簿から脱退して新家計簿に参加）— ※ TOP-3 の脱退仕様に依存
    - (B3) その他
- **影響**: ユースケース図の include 関係表現、参加 API のバリデーション、UI フロー。
- **関連指摘**: U-09 / TOP-3

### D. カテゴリ／固定費

#### QA-D1: カテゴリ削除時の既存明細の取り扱いは？

- **背景**: 「カテゴリを管理する（追加・編集・削除）」UC があるが、既に明細が登録されているカテゴリを削除した場合の挙動が未確定。
- **問い**: カテゴリ削除時、そのカテゴリに紐付く明細はどうしますか？
  - (A) 削除を拒否（先に明細を別カテゴリに付け替える運用を強制）
  - (B) 論理削除（カテゴリは非表示になるが、過去明細では「削除済みカテゴリ」として参照される）
  - (C) カスケード削除（明細も一緒に削除）
- **影響**: カテゴリエンティティの削除可否ロジック、`categories.deleted_at` 列の要否、UI 表示。

### E. 予算

- **回答**: **(B) 出さない** ✅（グラフでの事後確認のみ。登録フローはシンプルに保つ）
- **重要度**: Medium
- **背景**: 要件定義書 §4.1「現在月の累積支出グラフ ... 予算ラインも表示」とあり、グラフでは事後確認可能。一方、収支登録時にリアルタイムで「予算超過」を警告する仕様は未定義。
- **問い**: 収支登録時、そのカテゴリの月次予算を超過しそう／超過した場合、登録画面で警告を出しますか？
  - (A) 出す（モーダル警告 or インライン表示）
  - (B) 出さない（グラフでの事後確認のみ）
- **影響**: 「収支を登録する」UC から予算側への extend 関係の要否、登録 API レスポンスへの予算情報含有。
- **関連指摘**: U-12

#### QA-E2: 月内累積支出グラフで予算未設定カテゴリは？

- **回答**: **(A) はい（予算ラインなしで累積支出のみ表示）** ✅ → 図で `uc_viz_cumulative` から `uc_budget` への `<<include>>`（あるいは条件付き参照）を追加
- **重要度**: Medium-High
- **背景**: 要件定義書 §4.1「カテゴリ別月次予算が設定されている場合は予算ラインも表示」と記載があり、未設定時は予算ライン無しでグラフ表示する想定と読める。ユースケース図には予算 UC と月内累積 UC の include 関係が無い。
- **問い**: 月次予算が未設定のカテゴリについて、月内累積支出グラフは予算ラインなしで表示する想定で合っていますか？
  - (A) はい（予算ラインなしで累積支出のみ表示）
  - (B) いいえ、別の挙動を想定（具体的に）
- **影響**: ユースケース図に `uc_viz_cumulative` から `uc_budget` への include 関係を追加するか、ノートで明示。
- **関連指摘**: U-07

### F. 収支明細（登録・CSV インポート・固定費自動コピー）

#### QA-F1: CSV インポートの実行権限・重複検知は？

- **回答**:
  - (Q1-a) **(A) 管理者のみ** ✅ → CSV インポートのアクターは管理者に変更
  - (Q1-b) **(A) 重複検知あり** ✅ → 同日付・同カテゴリ・同額の組み合わせを検知し UI で確認を促す
- **重要度**: Medium
- **背景**: 要件定義書 §6.3「既存スプレッドシートの内容を CSV エクスポート → インポートする想定」。所有者カラムは CSV で指定されるため、メンバーが他者の明細を勝手に生成可能。複数メンバーが各々スプレッドシートを持ち込んで重複インポートする懸念。
- **問い**:
  - (Q1-a) CSV インポートの実行権限は？
    - (A) 管理者のみ
    - (B) 全メンバー
  - (Q1-b) 既存明細との重複検知は必要？
    - (A) 必要（同日付・同カテゴリ・同額の組み合わせを検知し、UI で確認を促す）
    - (B) 不要（重複は手動削除でカバー）
- **影響**: CSV インポート API の認可ロジック、重複検知のバッチ処理、UI の確認ダイアログ。
- **関連指摘**: U-10

#### QA-F2: 固定費自動コピー後の挙動（前月明細が無い場合）は？

- **回答**:
  - (Q2-a) 前月にそのカテゴリの明細が 1 件も無い場合 → **未確定**（暫定: コピーされない＝何もしない）
  - (Q2-b) **固定費フラグを ON にした月の月初コピーは「翌月から」有効** ✅ → ON にしたその月はコピー対象外、翌月以降にコピーが効く
  - (Q2-c) 月初コピー後に固定費フラグを OFF にした場合 → **未確定**（暫定: コピー済み明細はそのまま残る、ユーザーが手動削除）
  - ※ Q2-a / Q2-c は派生論点として記録。ドメインモデル設計時に再確認
- **重要度**: Medium
- **背景**: 「月初に前月分を自動コピー」とあるが、前月に該当カテゴリの明細が無かった場合や、ユーザーが月初前に固定費フラグを変更した場合の挙動が未確定。
- **問い**: 以下のケースの挙動は？
  - (Q2-a) 前月にそのカテゴリの明細が 1 件も無かった場合 → コピーされない／空の明細が作られる
  - (Q2-b) 月初コピー前にユーザーが固定費フラグを ON にした場合 → 翌月から有効／その月の月初分から有効
  - (Q2-c) 月初コピー後に固定費フラグを OFF にした場合 → コピー済みの明細はそのまま残る／削除される
- **影響**: 固定費自動コピーバッチの仕様詳細、ドメインの不変条件。
- **関連指摘**: U-19 派生

### G. 視覚化・分析

#### QA-G1: 視覚化機能の画面構成と粒度は？

- **回答**: **(A) 1 つの「分析ダッシュボード」画面でタブ切り替え** ✅ → ユースケース図の視覚化 UC 5 件を「家計簿を分析する」1 件に統合可能。各グラフは派生機能としてノートで列挙
- **重要度**: Medium
- **背景**: ユースケース図では月別収支推移・カテゴリ別支出割合・メンバー別支出比率・月内累積・カテゴリ別年間推移の 5 つを独立 UC として並べている。実画面構成（1 つの分析ダッシュボード or 各グラフ独立画面）が未確定。
- **問い**: 視覚化機能はどう提供しますか？
  - (A) 1 つの「分析ダッシュボード」画面でタブ・スイッチャー切り替え
  - (B) 各グラフが独立した画面・操作
  - (C) ホーム画面に主要 1〜2 グラフ常時表示、詳細は個別画面
- **影響**: ユースケース図の粒度（5 個維持 or 1 個に統合）、ルーティング設計、UI 設計。
- **関連指摘**: U-11

#### QA-G2: 「自分の収支のみ」フィルタの一覧画面は必要？

- **回答**: **(B) 不要** ✅（共通の収支明細一覧でフィルタ UI を提供すれば足りる）
- **重要度**: Low-Medium
- **背景**: 要件定義書 §4.1「収支確認」に「自身の収支データを確認できる」と記載。ユースケース図では「収支明細を管理する（閲覧・編集・削除）」UC の閲覧機能に吸収されている可能性があるが、明示されていない。
- **問い**: 「自分の収支のみ」「今月分だけ」のフィルタ付き一覧画面は必要ですか？
  - (A) 必要（独立画面 or タブ）
  - (B) 不要（共通の収支明細一覧でフィルタ UI を提供すれば足りる）
- **影響**: 一覧画面の UI 設計、API のクエリパラメータ仕様。
- **関連指摘**: U-15

### H. チャット・通知

#### QA-H1: チャット送信と Push 通知のトリガー関係は？

- **回答**: **(B) 個人設定で ON/OFF 可能（QA-A2 と連動）** ✅ → 「通知設定を管理する」UC を追加し、`uc_chat_msg` から `uc_chat_push` への通知発火は通知設定 ON のメンバーのみ
- **重要度**: Medium-High
- **背景**: 業務フロー図「チャット送受信 → LINE 公式アカウント Push 通知 → 他メンバー宛に通知」が描かれているが、ユースケース図では `uc_chat_msg` と `uc_chat_push` が独立 UC として並ぶだけで include 関係が無い。
- **問い**: チャット送信時の Push 通知の挙動は？
  - (A) 送信時に他メンバー全員に必ず通知（include 関係）
  - (B) 個別 ON/OFF 設定あり（QA-A2 と紐付く）
  - (C) ユースケース図では `uc_chat_push` を「システムの副作用」として削除し、業務フロー図側でのみ表現する
- **影響**: ユースケース図の関係性表現、`uc_chat_push` の存続可否。
- **関連指摘**: U-08

#### QA-H2: チャットの既読は誰の既読を見る？

- **回答**: **(A) 表示時に自動で既読化、他者の既読状況を画面上で確認可能（LINE 風）** ✅
- **重要度**: Low-Medium
- **背景**: 「既読状態を確認する」UC があるが、「自分が既読にする操作」なのか「他者の既読状況を見る」なのか曖昧。
- **問い**: 既読の扱いは？
  - (A) メッセージ表示時に自動で既読化、画面上で他者の既読状況を確認可能（LINE 風）
  - (B) ユーザーが明示的に「既読にする」ボタンを押す
- **影響**: 既読 API の発火条件、UI 設計。
- **関連指摘**: U-19 派生
